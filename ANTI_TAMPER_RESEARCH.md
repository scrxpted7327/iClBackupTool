# Anti-Tamper Decryption Research

## Target
`C:\deobfuscate\SpiderBackup.exe` — 1207 method bodies encrypted with ConfuserEx AntiTamper (Normal mode).

## PE Structure
| Section | VA | VirtSize | RawOff | RawSize |
|---------|------|----------|--------|---------|
| `.text`  | 0x2000 | 0xBB0B8 | 0 | 0 |
| `.5+.`   | 0xBE000 | 0xDE390 | 0 | 0 |
| `.zN\|`  | 0x19E000 | 0x136DDC | 0x400 | 0x136E00 |
| `.rsrc`  | 0x2D6000 | 0x2EF64 | 0x137200 | 0x2F000 |

`.text` and `.5+.` have `RawSize=0` — their encrypted data lives in the `.zN\|` section's raw data at file offset 0x400.

## Method Counts
- **Total with RVAs:** 1207
  - **Early** (`.text` + `.5+.`, RVA < 0x19E000): 544
  - **Late** (`.zN\|`, RVA >= 0x19E000): 663
- **Reflected (correct bodies via `Assembly.Load`):** 605

## File Layout in `.zN\|` Block
All 1207 encrypted method bodies are packed sequentially into the `.zN\|` raw data block (offset 0x400, size 0x136E00 = 1,273,344 bytes). The first 431,828 bytes contain the 544 "early" methods (`.text` then `.5+.` in token order). The remainder contains the 663 `.zN\|` methods.

### Early Method Position Finding
`.text`/`.5+.` methods are in token order at the start of the block. Their positions were found via:
1. Compute cumulative expected offsets from RVA gaps between consecutive early methods
2. Scan ±200 bytes around each expected offset for a valid CLI header byte (`(dec[0] & 3) ∈ {2,3}`)
3. For methods past the RVA-gap bound, scan sequentially from the end of the last found method

All 544 early methods were located with this approach.

### `.zN\|` Method Positions
`.zN\|` methods are at file offset = `0x400 + (RVA - 0x19E000)`. Found directly via `rvaToFileOff`.

## Encryption Scheme
**Type:** AES-CTR (ConfuserEx AntiTamper Normal mode)

**Key insights:**
1. Each byte in the block is XORed with a keystream byte: `ciphertext[i] = plaintext[i] ^ keystream[i]`
2. The keystream is generated by AES in CTR mode with a 32-byte key
3. The keystream is **position-dependent** (non-repeating): `keystream[i] = AES(key, nonce || counter[i/16])[i%16]`
4. XOR key derived from longest matching pair (5956 bytes) is the keystream at that position
5. Using `xorKey[i % keyLen]` for ALL methods only works when the method's position aligns with the key reference position modulo the CTR block size

**Evidence for position-dependence:**
- Stream key bytes at different block positions do NOT match (only ~1.5% periodic correlation vs 0.4% random)
- Per-token key first-byte distribution: 0x33 (253), 0x11 (245), 0x60 (30), 0x3B (17), 0x10 (15) — heavily skewed, reflecting position-dependent keystream
- Only ~63/602 non-reflected methods produce valid IL via cyclic XOR fallback

## Key Recovery (Unresolved)
The AES key is stored in the ConfuserEx anti-tamper runtime, probably XOR-encoded with a pattern like:
- `key[i] ^= (byte)i`
- `key[i] ^= (byte)(i ^ 0x55)`
- `key[i] ^= (byte)(i * 0xEB)`

The encrypted key blob is likely in:
1. The `.zN\|` section at a calculated offset (try section header/footer)
2. A static byte array in one of the 605 reflected anti-tamper runtime methods
3. A resource embedded in the assembly

If the key is found, decrypting the entire section requires:
1. Reconstruct AES-CTR keystream for all byte positions
2. XOR each ciphertext byte with the keystream
3. Parse decrypted bodies and write as `.dec_xor` files
